## Public write keys

Analytics keys are public, project-scoped, and write-only: they can
submit events and identity operations for ONE project and can never read
data, manage accounts, or access other projects. The project is derived
from the key on every request.

## Dashboard sessions

Dashboard access uses HTTP-only cookie sessions signed with
`JWT_SECRET_KEY`. Sessions are scoped to the product API.

## Service JWTs

The analytics WebSocket authenticates with short-lived service JWTs
issued by the product API and verified against the published JWKS —
issuer, audience, signature, and expiry. The subject must be an active
user, and the subscription is authorized through project and team
membership.

## CORS

The analytics ingestion API answers any origin; requests are
authenticated by the write key. The product API restricts CORS to the
configured origins.

## Rate limits

Ingestion is bounded per IP (120 requests/minute) plus an event-weighted
per-project quota; WebSocket upgrades are bounded per IP (30/minute).
Exceeded requests receive `429` with `Retry-After`.

## Trusted proxies

Forwarding headers are trusted only when the immediate peer is a
configured trusted proxy. The bundled nginx overwrites
`X-Forwarded-For` with the real peer address and clears
`CF-Connecting-IP`; direct deployments use the socket peer. Forged
headers cannot rotate the per-IP rate-limit key.

## Stored secrets

Analytics keys, auth tokens, and database credentials are never stored in
the analytics store or returned by any API. Logs redact IP-like values
and never include keys, bodies, or stack traces.

## Optional integrations

Mail, geo enrichment, external storage, and social providers run only
when configured. Each integration's credentials are environment
variables, never committed.

## Responsible disclosure

Report security issues privately to the maintainers. Do not open public
issues containing exploit details or real credentials.
