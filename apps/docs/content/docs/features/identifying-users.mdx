Prism links activity to **people**. A person starts as an anonymous
identity generated by the SDK and becomes known when you call
`identify()` with your own user ID. This page covers the identity model,
the SDK operations, and the People dashboard, including export and
deletion.

## Anonymous identity

Every client starts with an anonymous ID. With the default persistence
mode it survives reloads in the same browser profile; choose a stricter
mode through the client's `collection.anonymousPersistence` option.
All pre-identify events attach to this anonymous identity.

## `identify(userId, traits?)`

```ts
const result = await prism.identify("user_123", { plan: "pro" });
// { status: "queued", opId, userId, anonymousId } | { status: "dropped", reason }
```

One ordered operation: the current anonymous identity links to the
external ID, traits apply, and immediately-following `track()` events
carry the user ID. The operation queues and retries idempotently.

- **Multi-device**: one user ID may link many anonymous IDs. Events
  resolve to the person by user ID; pre-identify history links through
  the anonymous identity. Historical events are never rewritten.
- **Shared devices**: an anonymous identity is never silently re-linked
  to a second person. `identify(B)` after `identify(A)` rotates to a
  fresh anonymous context — two known people are never merged.
- **Traits**: set or update with `identify(userId, traits)`; remove with
  `identify(userId, { $unset: ["old_key"] })`.

## `reset()`

```ts
await prism.reset(); // logout semantics
```

Closes the session, clears the known identity, rotates the anonymous
ID, and clears queued identify operations and all global-property
scopes. The next user on a shared device never inherits the previous
user's context. Queued events keep their immutable identity context.

## What Prism never captures

The SDK does not collect emails, names, or any profile field you do not
pass explicitly. Traits are developer-supplied JSON values, sanitized
like event properties.

## The People dashboard

Identified people appear on the project's **People** page after an
`identify()` call — anonymous-only traffic never appears as a People row.

- The **summary strip** counts identified people (all time), identified
  people active in the selected 7/30/90-day range, people first identified
  in the range, and anonymous-only subjects active in the range. Each
  number states exactly what it covers.
- The **people list** leads with what the developer supplied: a display
  name, username, or email from explicit traits, with the external user ID
  alongside. Search matches the exact developer-supplied user ID — no
  fuzzy name or email search.
- A **person profile** shows supplied traits, linked identities (anonymous
  history collapsed by default), a sessions/events summary, and the
  person's source-aware event timeline. Rows open the same event detail
  view as the Events page.
- **Export** produces a complete copy of the person's data — identity
  links, traits, sessions, events, and error occurrences — for
  data-portability requests. Owner and admin only.
- **Delete person** permanently removes identity links, traits, sessions,
  and events. The action is owner/admin only, requires typing `delete` to
  confirm, and a later `identify()` with the same external ID creates a
  new person with a clean slate — deleted history never silently returns.

The page never shows Prism's internal person ID as an identity. It stays
in the profile's technical details, where it belongs.

## Troubleshooting People

- **No rows appear.** People appear only after the SDK calls
  `identify()` with a user ID and the call queues successfully. Check the
  console diagnostics for `identify_rejected` or consent drops, and
  confirm the events actually arrive (the Events page should show the
  identified events).
- **Two rows for one user.** The same external user ID resolves to one
  person per project. Two rows usually mean two different user IDs were
  sent — for example a raw email on one platform and an opaque ID on
  another. Pick one stable, application-owned ID and use it everywhere.
- **Missing traits.** Traits update only through
  `identify(userId, traits)`. Re-identify with the traits you want set;
  remove stale keys with `$unset`. Prism never fills traits from event
  properties.
- **Wrong user after logout.** Call `reset()` on logout and account
  switching. Without it, the next user on the device inherits the
  previous identity's links.
- **Deleting data.** Deletion is permanent and project-scoped: the same
  external ID in another project is a different person and is not
  affected.

## Consent and identity

`identify()` respects the consent state machine: with collection denied,
identify operations are dropped. See
[Consent and privacy](/docs/configuration/consent-and-privacy) for the
state machine and persistence choices.
