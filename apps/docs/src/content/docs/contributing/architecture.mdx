## The two-store boundary

Prism deliberately separates **product state** from **analytics data**:

| Store | Owns | Accessed by |
| --- | --- | --- |
| Product database (PostgreSQL) | users, teams, memberships, projects, API keys, profiles | product API (auth + dashboard) |
| Analytics store (sqld/libSQL, or Turso) | sessions, events | analytics API (ingestion), product API (reads) |

The product API reads analytics through a **runtime adapter**, so a missing
or unreachable analytics store degrades reads only (empty analytics, working
rest of the instance). This boundary is what makes the analytics store
optional in self-hosting.

## Runtime adapter model

Several seams make the same code run on Workers and Node, and hosted and
self-hosted:

- **Database**: `DatabaseManager` resolves a runtime driver (neon-http on
  Workers, postgres-js in Node) behind one query surface.
- **Storage**: `StorageManager` selects imagekit / s3 / local drivers for
  avatar uploads and `/files/*` serving.
- **Analytics store**: `TursoDatabaseManager` (and `NeonDatabaseManager`
  fallbacks) behind the analytics read surface.
- **Config**: one `resolvePrismConfig(env)` validates and resolves every
  environment contract; invalid config fails fast at boot with variable
  names (never values).
- **Mail**: SMTP/Resend/log-only channel behind one schedule API.

## Auth

Better Auth, one shared `buildAuthOptions` used by the Worker runtime, the
CLI, and tests. UUID ids, text-keyed tables, provisioning hooks (profile +
personal team created idempotently after user creation), JWT plugin for
realtime service tokens. See [Authentication](/hosted/authentication/).

## Deployment modes

The same build serves two topologies: hosted (Cloudflare Worker + managed
stores) and self-hosted (Compose: postgres + migrate + api + sqld +
analytics + web behind one origin). See the [self-hosting overview](/self-hosting/overview/) and
[ADR 0001: deployment modes](https://github.com/OrekuD/prism/blob/main/docs/adr/0001-deployment-modes.md)
in the repository.
