<SectionLabel label="ENVIRONMENT CONTRACT" />


Every variable below is validated at boot by `resolvePrismConfig`: invalid
values fail fast with the variable name and remediation (never values).
This reference is generated from the validator, `.env.example`, and
`.dev.vars.example` — keep those three in sync.

## Required

| Variable | Requirement | Default | Mode | Secret | Applied |
| --- | --- | --- | --- | --- | --- |
| `DATABASE_URL` | PostgreSQL connection URL (plain or Neon-style pooled) | — | both | yes | boot |
| `JWT_SECRET_KEY` | Minimum 32 characters — `openssl rand -hex 32` | — | both | yes | boot |
| `CLIENT_URL` | Dashboard origin (CORS allowlist, email links); origin-shaped URL | — | both | — | boot |
| `BASE_URL` | Public API URL (cookies, callbacks, JWKS); origin-shaped URL | — | both | — | boot |
| `SETUP_TOKEN` | Required in self-hosted; minimum 16 characters | — | self-hosted | yes | boot |
| `PORT` | Node server port | `8787` | self-hosted | — | boot |

`BASE_URL` behind a reverse proxy must be the **external** origin users
reach (e.g. `https://analytics.example.com`), not an internal service name.

## Deployment mode

| Variable | Values | Default | Notes |
| --- | --- | --- | --- |
| `PRISM_DEPLOYMENT_MODE` | `hosted` \| `self-hosted` | `hosted` | Strict: anything else fails boot |
| `ENVIRONMENT` | `development` \| `production` | `development` | `production` enables Secure cookies; strict validation |
| `SIGNUP_POLICY` | `open` \| `invite-only` \| `disabled` | `disabled` (self-hosted) / `open` (hosted) | `invite-only` and `disabled` close public signup; invites + first-owner bootstrap remain |
| `INSTANCE_NAME` | Display name in auth shell, emails, config endpoint | `Prism` | Never hardcoded `Prism Cloud` |

`ALLOW_PUBLIC_SIGNUP` is the legacy alias for `SIGNUP_POLICY` (hosted
compatibility).

## Analytics store

| Variable | Requirement | Default |
| --- | --- | --- |
| `TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN` | Optional | — |
| `ANALYTICS_RETENTION_DAYS` | Non-negative integer; unset/0 disables retention deletion | `0` (disabled) |

Without the store, analytics reads return empty and the rest of the instance
works (one-time warning at boot). Self-hosted defaults to the bundled sqld
container; set these only when using Turso.

## Retention

`ANALYTICS_RETENTION_DAYS` controls deletion of expired analytics data.
**Unset or `0` disables deletion** (the default — no surprise data loss); a
positive integer enables batched deletion of sessions (and their events)
older than that many days. Events are deleted before sessions, in one atomic
batch.

Run it from the analytics container (or locally against your store):

```sh
docker compose exec analytics node dist/src/retention.js --status
docker compose exec analytics node dist/src/retention.js --dry-run
docker compose exec analytics node dist/src/retention.js
```

- `--status` prints configuration and row counts (read-only).
- `--dry-run` prints what would be deleted without deleting.
- The plain invocation applies the deletion and reports affected rows.
- Invalid values (negative, non-integer) fail fast at invocation.

Schedule it (e.g. a nightly cron) once you have chosen a window. Deleted
data cannot be recovered — keep a volume snapshot if you need a safety net
(see [Backup & restore](/docs/self-hosting/operating/backup-restore)).

## Secrets & rotation

- Generate: `openssl rand -hex 32` (`JWT_SECRET_KEY`), `openssl rand -hex 24`
  (`SETUP_TOKEN`), and a strong `POSTGRES_PASSWORD`.
- Rotating `JWT_SECRET_KEY` invalidates all sessions — rotate during a
  maintenance window.
- `SETUP_TOKEN` is only read at first boot; it can be removed from the
  environment after the owner exists (the endpoint closes permanently).
